# V2 maintenance and release guide

## Environments

- `preview` is the shared development branch. Preview is https://preview.pcds2030.com.
- Local development and `npm run build:preview` enable V2 through tracked mode files.
- `main` and https://pcds2030.com remain V1 until production approval.
- The older `codex/v2-review` branch and https://v2.pcds2030.com are historical review snapshots. Do not use them as the base for new data changes.
- Internal `xai` and `concept` names remain for compatibility. No query parameter is needed on Preview.

## Maintenance

Codex maintains interface behavior and release workflow. Cursor maintains milestones,
status, descriptions, sources, translations and update history. Both start focused
branches from the latest `origin/preview` and use pull requests into `preview`.
The canonical data rules remain [the data methodology](data-methodology.md).
Do not copy older data files from the V2 review branch over current Preview data.

Run `npm run check:content`, `npm run lint`, and `npm run build:preview` before release.
Check Projects, Updates and About in English and Malay, including desktop and mobile.
Use `npm run preview` to inspect the built routes directly.

## Interface

V2 uses a sticky navigation bar, centred Projects and Updates heroes, teal accents,
and an article layout for About. Mobile navigation includes the language selector.
The initial navbar transforms into a compact logo before Projects content enters.
Status, Milestones and Links reveal letter by letter before settling on Tracker.
The description follows. Reduced motion shows the final content directly.
The navbar does not replay on internal navigation; the Projects entrance does.
Expanded milestones retain the original dated rows and remaining-item bullets.
The experimental timeline and replacement bullets were rejected and are not included.

## Migration and versions

The integration starts at Preview commit `024516d` and merges V2 commit `b8ef06a`.
Current Preview data and automation instructions are retained. This is an interface
migration, not a project-data audit.

Use `v2.0.0-rc.1` for the first GitHub prerelease on Preview. Use `v2.0.0` only after
production review and approval. A push alone does not create a GitHub release.
Before promoting to main, explicitly decide how the production build enables V2,
verify indexing and route metadata, then follow the normal release approval process.

Historical design experiments are recorded in [the archived design study](xai-concept.md).
